# 诗矩 Windows 在线安装与首次使用规范（讨论稿）

编制日期：2026-10-30。状态：研究与设计建议，尚未批准实施。

本文基于微软 Windows 桌面应用建议、Inno Setup 官方文档及当前诗矩部署流程整理。它不是微软颁布的一份统一强制标准，也不意味着下列功能已经实现。

“必须”表示本项目建议的验收门槛；“建议”表示可分期实施。涉及具体默认路径、安装器选型和下载顺序的内容均为诗矩的设计建议。

## 1. 产品目标与改造边界

目标：用户不理解 Python、Conda、PyTorch、CUDA，也能够完成安装、失败后恢复、开始使用和卸载。

采用在线按需下载：安装入口只携带启动与部署必需的文件，按检测结果下载 CPU 或 GPU 运行组件、所选模型。无需将所有环境和模型预装到发行包。

优先保留现有模型校验、固定依赖、下载校验、环境隔离和生成验证逻辑。先规范入口、文案、目录选择、状态显示与恢复动作；不得为美化界面重写推理核心。

“安装器”负责程序文件、快捷方式、卸载和版本识别；“部署器”继续负责运行环境与模型。两者不能分别维护互相冲突的安装状态。

微软建议遵循标准 Windows 行为、支持当前用户安装并提供系统卸载入口。[S1]

## 2. 对用户的统一称呼

| 内部概念 | 主界面称呼 | 详情中的补充 |
|---|---|---|
| Python、PyTorch、依赖包 | 运行组件／运行环境 | 可查看具体版本 |
| CUDA 推理 | GPU 加速 | 显示实际显卡名称 |
| CPU 推理 | CPU 模式 | 提醒速度与内存要求 |
| checkpoint、plan、manifest | 自动保存的安装进度／安装方案 | 仅在诊断详情展示原字段 |
| verification | 检查是否能够正常运行 | 说明正在加载模型还是测试生成 |

模型大小、下载量、资源要求是用户需要的选择依据，不应全部隐藏；依赖包名称与堆栈默认收进详情。

统一产品名、图标、发行者、版本号和帮助入口。“诗矩安装”“准备运行环境”“诗矩”三个阶段名称可以不同，但必须说明其关系。

## 3. 入口、权限与系统登记

必须：

- 提供一个面向普通用户的安装入口，用户无需判断多个 BAT、EXE、PS1 谁先运行。
- 默认面向当前用户安装和运行。仅在安装确实需要提权的系统组件时单独请求管理员权限，事先解释原因；不得整个部署过程一律管理员运行。
- 安装后在开始菜单建立稳定启动入口；桌面快捷方式可选，不默认添加开机自启。
- 常规安装模式下，在 Windows“已安装的应用”登记产品名、版本、发行者和卸载入口。
- 安装器被重复启动时，识别已有任务并引导返回，不能同时向同一目录安装。
- 普通用户无需保留原下载包才能启动软件。便携模式若保留，应单独命名并说明保留整个文件夹。

Inno Setup 支持非管理员安装；其默认权限是 admin，不能直接照搬默认值，需要明确选择。安装权限模式还会影响卸载信息登记位置。[S2][S3]

## 4. 用户可见流程

建议普通流程为：

1. **欢迎与安装位置**：说明联网下载，软件位置、资源位置可查看和调整。
2. **检查电脑**：检查操作系统、目录权限、资源条件；明确“硬件识别通过”不等于“GPU 已验证”。
3. **确认安装方案**：显示模型、CPU／GPU、预计新增下载量、各盘空间及安装位置。
4. **下载并准备组件**：自动执行，支持停止和恢复。
5. **检查能否运行**：组件运算检查、模型加载、实际生成。
6. **开始使用**：只有全部必要验收通过才允许显示“已准备就绪”。

也可采用“先安装程序，再首次启动准备组件”的两阶段流程，以降低安装器与部署器耦合。必须明确区分“程序文件已安装”和“运行环境已就绪”，不得在后者失败时仍宣传全部成功。

一页只要求用户做一类决定；模型、路径等高级设置可折叠。初次安装不强迫用户导入清单、选择 Python 版本或指定包源。

## 5. 目录规范：用户选位置，程序组织内容

推荐长期结构：

| 内容 | 推荐位置原则 | 用户是否常用 |
|---|---|---|
| 程序文件 | 当前用户可写的专用程序目录，如 LocalAppData 下的 Programs/ ShiJu，或经用户选择的专用目录 | 通常不操作 |
| 设置、会话、安装记录 | 当前用户 LocalAppData/ ShiJu，沿用既有兼容位置优先 | 通过程序管理 |
| 模型、独立环境、下载缓存 | 用户确认的资源根目录下分别建立 models、environments、cache | 可选择所在磁盘 |
| 用户创作与导出 | 用户明确选择的位置 | 应保留 |
| 临时下载 | 明确归属的临时／缓存区域 | 可通过界面清理 |

以上为建议结构，并非要求第一期迁移现有数据。

必须：

- 明确区分“程序位置”“模型位置”“运行环境位置”“下载缓存位置”。若合并成一个“资源保存位置”，必须显示最终子目录预览。
- 用户选 D 盘时，不得让其以为所有大文件都在 D 盘，实际却把数 GB 缓存放在 C 盘。第一期不改缓存路径也可以，但必须提前明确 C 盘预算。
- 用户选择父目录后，是直接使用它，还是在其中新建 ShiJu 子目录，必须在选择器及确认页写清楚。
- 现有模型目录采用“使用已有模型”动作，不能混同“新下载保存位置”。
- 不得将模型目录当作环境目录；路径冲突在下载前指出。
- 检查空路径、相对路径、文件误当目录、无权限、根目录、目录包含关系、当前空间和临时展开峰值。
- 对目录建立或写入能力做可恢复的小规模检查，不只看磁盘存在。
- 当前若不支持中文路径，要在填写路径时明确标注并提供可行位置；不得要求用户改 Windows 用户名。中文路径支持属于独立兼容性任务。

遇到非空目录时，至少显示完整路径、无法复用的原因及“选择其他目录”入口。不得引导用户笼统删除整个目录。可以建议一个不存在的新子目录，用户确认后再使用。

## 6. 安装前确认页

必须同时回答：

- 安装什么：诗矩版本、所选模型、CPU／GPU 模式。
- 保存哪里：所有实际使用的位置，可复制或展开查看。
- 下载多少：已有可复用、仍需下载、总计；未核验的文件不能算作已可复用。
- 占用多少：下载缓存、最终安装占用、临时解压峰值；按磁盘合并计算，避免重复相加或漏算。
- 有什么代价：CPU 速度可能较慢，较大模型需要更多内存，GPU 仍待实际验证。
- 下一步是什么：按钮为“开始安装”或“下载并安装”。

默认方案应能够解释。电脑能用更大模型仅作为选项，不作为阻断当前可用方案的警告。

## 7. 按钮、返回、取消与关闭

微软桌面交互建议优先使用表达具体动作的按钮，避免用户必须读完正文才能猜出按钮意义。[S4]

| 场景 | 推荐按钮 | 明确禁止的歧义 |
|---|---|---|
| 可选更大模型 | 保留当前方案／调整模型 | 裸露“是／否” |
| 风险确认 | 继续安装当前方案／返回调整方案 | “确定”却暗含更换方案 |
| GPU 不可用 | 改用 CPU 方案／重新检测 GPU | 用户不知道重试会做什么 |
| 网络失败 | 重试下载／返回方案 | 失败后仅允许退出 |
| 已有安装 | 继续安装／检查并修复 | 无说明直接覆盖 |
| 安装中关闭窗口 | 停止并退出／继续安装 | 直接终止写文件 |

必须分别定义：

- 返回：回到上一步，保留输入和已验证文件。
- 停止：停止当前任务，保存可恢复状态，不宣称完成。
- 退出：关闭程序。若仍在写入，先进入“正在停止，请稍候”。
- 清理：单独的明确动作，不是取消的隐含副作用。

未开始耗时操作时取消不必反复确认；正在安装且会中断操作时可以确认，但必须说明已下载文件能否保留。任何按钮点完后，页面都必须处于用户知道下一步的状态。

## 8. 下载规范

必须：

- 显示当前下载对象、已下载／总量、速度；总量未知时不得伪造百分比。
- 网络超时有上限和可见的重试说明，不能无限无提示重试。
- 保留已通过校验的下载；部分文件只有在服务端及文件身份支持时才能断点续传，不能承诺所有来源都可续传。
- 下载完成后校验版本、大小或哈希；校验失败不作为成功文件使用。
- 下载到临时文件，校验通过再发布为有效文件，避免半包被识别为完整包。
- HTTPS 下载；更换镜像不能改变文件身份或绕过完整性校验。
- 离线时说明需要联网的具体步骤，允许保留已选方案或退出稍后继续。
- 不要求用户为下载关闭系统安全功能。

在线安装并非不规范：Inno Setup 官方下载接口支持 HTTPS、进度回调及 SHA-256 检查。是否使用该接口应服从已有下载器能力，不必为了安装壳替换成熟下载逻辑。[S5]

## 9. 进度规范

进度页应包含：当前阶段、正在处理的对象、已用时间、下一阶段，以及停止和详情入口。

能够准确量化的下载显示真实进度；模型加载等不能可靠估计的操作，显示阶段与耗时。不要把“完成 5 个阶段中的 4 个”写成“总耗时完成 80%”。

整体进度与当前文件进度分开标注；阶段切换不能让同一个看似整体的进度条反复归零。没有数据时不虚构剩余时间。微软的进度指南支持这些原则；该文档是旧版桌面设计指南，本文采用的是其反馈原则，不要求复制旧版视觉样式。[S6]

## 10. CPU／GPU 选择与复验

检测结果分为：硬件已识别、运行组件待安装、GPU 运算已通过、GPU 运算失败、条件变化需复验。不能把“发现 NVIDIA 型号”显示成“GPU 保证可用”。

必须：

- 按方案下载固定 CPU／GPU 组件，不同时无条件下载两套大包。
- PyTorch 准备好后检查 GPU 初始化与实际小规模运算，失败时保留原始异常。
- 自动排查程序的显卡选择设置；只有显卡身份无歧义时才自动修正，不在多卡机器上擅自切换到任意显卡。
- 界面说明“当前环境无法使用 GPU”，避免永久判定显卡损坏。
- 用户确认改用 CPU 后，重新检查模型、内存、磁盘及下载预算；不能只改按钮名称或直接继续原 GPU 清单。
- CPU 不满足最低条件时说明原因，允许选择小模型或返回，不能保证降级一定成功。
- 记录硬件、驱动、工具与关键组件版本、验证时间、失败阶段、原始错误及诊断编号。
- 同等条件下默认推荐 CPU，手动选 GPU 时提醒并允许复验；条件变化后标记待复验，不因旧失败永久禁用 GPU。
- 已有验证通过的环境不能只因一次网络错误或模型生成错误而登记为 GPU 不可用。

GPU 兼容性判断仍交给部署器；安装器外壳不复制一套独立推荐算法。

## 11. 错误信息与诊断

主界面采用三层：

1. 一句话说明发生了什么，例如“运行组件已准备好，但 GPU 检查未通过”。
2. 能确定的原因与可执行动作；没有把握时明确“尚无法确定”，不要编造缺失组件。
3. 展开显示原始错误、完整目标路径、日志和“导出诊断”。

示例：

> 无法在此目录创建运行环境。  
> 目录：D:\Example\models  
> 该目录已有文件，且不是可识别的运行环境。请选择一个新的空目录，已有文件会保留。  
> [选择其他目录] [查看详情]

必须：

- 错误文字可选择、复制、滚动；不能只有截图才能反馈。
- 指出真正失败的路径，日志位于 C 盘不能被误认为安装目标也是 C 盘。
- 记录发行版本、任务、阶段、组件版本、退出码、异常链与相关子进程结果。
- GPU 诊断包含实际显卡限制值、每次检查条件与结果，不能只有 cuda=false。
- 诊断包应带文件索引，能识别用户发来的是哪次安装，而非混淆多轮记录。
- 导出前说明包含本机路径和硬件信息；不自动上传，不包含密码、令牌或用户作品正文。
- “导出诊断”是辅助动作，不能取代“重试／更改方案”这样的直接恢复入口。

## 12. 安装状态与恢复规范

| 状态 | 必须具备的操作或说明 |
|---|---|
| 尚未开始 | 可以配置与开始 |
| 正在执行 | 当前任务明确，禁止重复开始 |
| 正在停止 | 等待子任务安全结束，不能假装已取消 |
| 已停止 | 继续安装／返回方案 |
| 当前步骤失败 | 重试当前步骤／调整方案／导出诊断 |
| 文件已准备、运行未通过 | 明确未就绪，可以修复 |
| 已就绪 | 启动诗矩／管理组件 |
| 检测条件变化 | 说明需要复验，不能混用旧通过记录 |

以上是用户可见状态约束，不要求为此重写现有内部状态机。优先把已有字段映射到清晰界面，只有存在恢复漏洞时才调整内部状态。

安装中断、崩溃或断电后，重新启动必须检查事实状态，而非盲信上次写入的“完成”。复用必须校验文件与清单身份。

“重试”只重复未完成工作；“重新开始”不是自动删除全部文件。重建环境应使用有归属的目录，旧可用环境在新环境验证成功前保留。

不能假定包装成 MSI／EXE 后，外部 Python 安装和下载也自动获得事务回滚。微软指出 MSI 自定义操作需要额外编写回滚支持；实际恢复边界必须单独设计。[S7]

## 13. 升级与修复

必须保持稳定产品身份，使安装器识别同一个软件，而不是每次升级创建新软件。Inno Setup 的 AppId、安装权限模式和位数共同参与应用身份识别，并可沿用原安装目录。[S8][S9]

要求：

- 展示当前版本与待安装版本。重新安装同版本应有“检查并修复”语义；低版本覆盖不能无声发生。
- 程序升级、运行组件升级、模型下载是不同任务，分别展示影响。
- 原模型通过校验即可复用；不因为安装包版本号变化而重新下载全部模型。
- 只有运行组件清单或兼容条件改变，才要求对应环境更新／复验。
- 更新失败要有恢复到可用版本的办法；第一期可先使用保留旧包的完整替换，不必马上开发后台自动更新。
- 更新前处理正在使用的文件和运行任务；不得直接终止用户正在生成的任务而不解释。
- 原便携目录、C 盘与 D 盘多份安装都要展示实际路径，不能任意猜测“最新环境”。

修复入口应能检查文件、重试失败组件、打开日志；不要让普通用户手工运行 pip 或编辑 JSON。

## 14. 卸载与清理

建议卸载界面明确分项：

- 程序与快捷方式：卸载。
- 运行环境：可选删除，显示位置及估算占用。
- 模型：默认保留，可选删除。
- 下载缓存：可选清理，显示可释放空间。
- 用户作品及导出：默认保留，外部用户目录绝不递归删除。

删除前必须有目录归属记录和边界检查。共享模型、多版本复用环境以及用户自行提供的目录不能按“安装目录的所有东西”粗暴清理。取消清理不应妨碍程序卸载。

卸载后移除自身快捷方式、卸载登记和程序拥有的临时文件；保留项写明位置，重新安装时能够发现并核验复用。不擅自卸载用户已有 Python、Conda、显卡驱动及可能共享的系统运行库。

## 15. 发布质量与信任

必须具备明确版本、发行说明、完整文件清单和构建可追踪信息；不携带开发者私有配置、绝对环境路径、密钥与缓存。

公开正式分发建议规划代码签名和可信发布渠道。签名用于验证来源与完整性，不承诺系统绝不提示警告，也不能代替下载校验。[S10]

第三方组件与模型的许可证、分发条件和必要声明需要随选用情况核对，不能因为按需下载就省略。无需第一期引入复杂授权页面，但应提供可查阅的许可说明。

静默安装可作为后续管理能力：必须定义参数、日志和退出码，不能在无人值守模式下偷偷改 CPU／GPU 或弹出等待输入的窗口。

## 16. 改造分级与建议次序

| 阶段 | 内容 | 主要影响 | 核心风险 |
|---|---|---|---|
| A：引导规范化 | 术语、按钮、路径说明、错误三层展示、返回与停止反馈、统一入口说明 | 现有界面 | 较低，但仍需验证操作状态 |
| B：安装器外壳 | 复制原发行文件、稳定启动入口、快捷方式、卸载登记、版本识别 | 打包与系统集成 | 中等；权限和卸载要认真测试 |
| C：资源管理 | 统一资源根目录、可移动缓存、环境切换、旧版本迁移 | 路径与持久状态 | 较高；独立设计，不能顺带改 |
| D：自动维护 | 自动更新、后台修复、复杂组件回滚、多安装实例整合 | 生命周期管理 | 较高；后续迭代 |

建议先做 A，再用 Inno Setup 等成熟工具做 B 的可验证原型。Inno Setup 是候选，不是已决定的技术路线；是否满足许可证、发布和构建要求应在选型时确认。

第一期保持现有核心调用契约：安装壳传递目录与启动参数，部署器报告进度与结果。避免在安装器脚本里再实现模型下载、GPU 判断或依赖安装。

不要把“改几个文案”和“统一磁盘路径／迁移旧环境”混成一个改造。前者能较轻实施，后者涉及真实行为和恢复，需要独立验收。

## 17. 最小验收矩阵

采用干净 Windows 虚拟机测试安装集成，开发机或 CI 做可控故障注入，少量真实 GPU 机器验证计算能力；无需逐台用户电脑反复人工调试。虚拟机不能替代所有真实 GPU 运算测试。

| 类别 | 至少覆盖的场景 | 通过标准 |
|---|---|---|
| 首次安装 | 无 Python／Conda；标准用户；CPU／支持的 GPU | 一条引导路径可完成 |
| 路径 | C／D 盘、空格、不支持的中文路径、无权限、非空目录、模型环境重叠 | 下载前说明具体路径与处理办法 |
| 磁盘 | 目标盘空间不足；系统盘缓存不足；下载中空间不足 | 不假报成功，不破坏已有数据 |
| 网络 | 离线、超时、断流、镜像失败、损坏下载 | 可重试，校验有效，已有完整文件复用 |
| GPU | 驱动缺失、初始化失败、显卡限制错误、多卡歧义、运算失败 | 具体错误、CPU 入口、无错误永久封禁 |
| 记录 | 失败后再安装、手选 GPU、驱动更新、工具更新 | 推荐与复验策略一致 |
| 交互 | 返回、停止、关闭、重复点击、重复启动 | 无消失入口、无假忙碌、无并发写入 |
| 恢复 | 下载、安装、验证时中断；已有不完整环境 | 能继续或明确重建，不盲目全部重下 |
| 升级 | 同版本修复、新版本升级、运行中升级、升级失败 | 模型复用，版本明确，有恢复办法 |
| 卸载 | 保留模型、删除自有环境、外部模型、多份安装 | 只删除确认且有归属的数据 |
| 展示 | Windows 缩放 100%／150%／200%、键盘操作、长错误 | 按钮可达、文字可读、详情可复制 |

每一期按影响选择测试：纯文案优先界面走查；安装外壳必须补干净机器的安装／卸载／升级；路径迁移必须补数据完整性与恢复。复用现有核心测试，不为包装外壳重复建立一套推理正确性测试。

发布门槛：普通用户知道接下来点什么；失败时仍有动作入口；所有大文件位置和预算透明；无用户数据误删；成功必须代表真实验收通过。

## 18. 实施前需要定下的产品决定

1. 第一阶段只规范现有部署界面，还是同时增加安装器外壳？
2. 采用安装程序与首次准备组件分开的两阶段体验，还是一个窗口连续完成？
3. 先保持现有缓存位置并明确预算，还是单独安排资源路径改造？
4. 是否保留便携版，以及普通用户默认下载哪个版本？
5. 模型、环境、缓存卸载时的默认保留策略是否采用本文建议？

这些决定应在实施前明确。本文不以讨论稿代替用户批准，也不要求现在一次性做完所有阶段。
